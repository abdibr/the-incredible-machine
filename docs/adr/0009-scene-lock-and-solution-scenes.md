# Scene content is player-locked, and every level ships a proven solution scene

The pin/anchor affordances (issues #66/#67) left "escape hatches" in the player postures: outside sandbox authoring, a pinned part kept its pin handle and an anchored part its anchor handle — so a player solving a campaign level could unpin the goal bucket or un-anchor and drag the target ball, then press Play to win (cheating) or destroy the author's machine. Separately, level definitions carried no proof of solvability: nothing in the JSON or the loader said the level could actually be won. We decided two things:

1. **Scene content is untouchable in player postures.** Level-author content (`fixedObjects` rows → the new `isScene` lifecycle flag) offers no selection handles at all outside the sandbox authoring posture: not movable, not rotating, not deletable, and — the actual cheat — not un-pinnable or un-anchorable into a movable part. The sandbox keeps the full authoring affordances (issues #66/#67 stand there); player-authored pinned/anchored parts (pinned in-session, not scene content) keep their unpin/unanchor escape. Play (`PLAYING`) was already fully non-interactive and stays so.

2. **A level definition is two scenes: the puzzle and its solution.** Level JSON gains a required `solution: { scene: [...] }` — the full solved board in the placed-snapshot row shape (fixed rows + placed rows, rope knots as attachment tokens). The sandbox editor captures it automatically: when a sandbox play of the loaded level is won, the play-start snapshot is stamped as the solution candidate and `Save Level` writes it as `solution.scene`. Saving without a capture still works but produces an explained **draft** (`solution: null`): the sandbox editor's own Load is lenient by design, so a draft re-opens there, and winning a Test Puzzle run of the loaded draft captures the proof for the next Save — while the campaign loader and the player-import path refuse solution-less files, so no player ever receives an unproven level. The player-facing `Give Up` control (player postures only, also offered on the fail overlay) swaps the board to the solution scene in a new read-only `SOLUTION` posture (drag disabled, not runnable — the goal checker cannot be reached from it, so watching the solution never marks the level complete); `Return` (the give-up control relabeled, or Reset) rebuilds the user's attempt from the snapshot taken at give-up time.

## Consequences

- `LevelManager._validate` requires `solution.scene`, so the campaign loader and the player-import path (`validateCustom`) refuse solution-less levels with a readable error; the sandbox editor's own Import stays lenient (repair posture, unchanged). Custom saves made before this change no longer pass player import until re-saved from the editor after solving.
- Solution scenes are proven, not presumed: `tests/solution-scenes.test.js` replays every shipped level's solution scene in a headless engine and asserts `goal:reached` — a scene edit that breaks solvability fails CI.
- `restorePlacedFromSnapshot`'s level-branch skip rule keys on `isScene` (with a legacy fallback for rows that predate the flag), which also fixes the pre-existing quirk that a player-pinned part vanished from the edit board after play/reset: unmarked pinned rows are player content now and restore.
- Watching the solution grants no completion credit by construction (the `SOLUTION` posture never runs the simulation), so progression stays solved-it-yourself only.
